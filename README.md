# Cryptographic Communication Protocols

A Python-based implementation of cryptographic communication protocols using RSA, Diffie–Hellman (DH), and AES.

This project implements four protocols to demonstrate RSA key verification, secure key exchange, encrypted communication, and error detection.

## 1. Project Overview

The project consists of four cryptographic communication protocols between two participants, **Alice (Client)** and **Bob (Server)**.

Each protocol demonstrates a different aspect of cryptographic communication.

| Protocol | Description | Main Algorithms |
|---|---|---|
| Protocol I | RSA Key Generation and Verification | RSA |
| Protocol II | RSA-Based AES Key Exchange | RSA, AES-256 |
| Protocol III | Diffie–Hellman Key Exchange | DH, AES-256 |
| Protocol IV | Invalid DH Parameter Detection | DH Parameter Validation |

## 2. Protocol Implementation

### Protocol I: RSA Key Generation and Verification

**Objective:** Verify the mathematical correctness of an RSA key pair generated by Bob.

**Procedure:**

1. Alice requests RSA key generation from Bob.
2. Bob randomly selects two distinct prime numbers, `p` and `q`, between 400 and 500.
3. Bob calculates the RSA public exponent `e` and private exponent `d`.
4. Bob sends `p`, `q`, `e`, and `d` to Alice.
5. Alice verifies the validity of the received RSA parameters.

**RSA Key Generation:**

- Calculate the modulus: `n = p × q`
- Calculate Euler's totient: `φ(n) = (p − 1)(q − 1)`
- Select `e` such that `gcd(e, φ(n)) = 1`
- Calculate `d` such that `(e × d) mod φ(n) = 1`

**Verification Conditions:**

- Both `p` and `q` are distinct prime numbers between 400 and 500.
- The public exponent `e` is relatively prime to `φ(n)`.
- The public and private exponents satisfy `(e × d) mod φ(n) = 1`.

- `new_bob.py`

### Protocol II: RSA-Based AES Key Exchange

**Objective:** Securely transmit an AES key using RSA and establish encrypted communication.

**Procedure:**

1. Alice requests RSA-based communication.
2. Bob generates an RSA key pair and sends the public key `(n, e)` to Alice.
3. Alice generates a random 32-byte AES-256 key.
4. Alice encrypts each byte of the AES key using Bob's RSA public key.
5. Bob decrypts the encrypted values using his RSA private key.
6. Alice and Bob use the same AES key to encrypt and decrypt messages.

**RSA Encryption:**

`c = m^e mod n`

**RSA Decryption:**

`m = c^d mod n`

**AES Communication:**

- Encryption mode: AES-256-ECB
- Key length: 256 bits (32 bytes)
- Block size: 128 bits (16 bytes)
- Padding: PKCS#7
- Encoding: Base64

Messages are padded, encrypted with AES, and encoded in Base64 for JSON transmission. The receiver reverses these operations to recover the original message.

**Files:**
- `new_alice_2.py`
- `new_bob_2.py`
- `common_2.py`

### Protocol III: Diffie–Hellman Key Exchange with AES

**Objective:** Establish a shared AES key without directly transmitting the secret key.

**Procedure:**

1. Alice requests DH-based communication.
2. Bob selects a prime number `p` and a generator `g`.
3. Bob generates a private key `b` and public key `B`.
4. Bob sends `(p, g, B)` to Alice.
5. Alice verifies the prime number and generator.
6. Alice generates a private key `a` and public key `A`.
7. Alice and Bob exchange their public keys.
8. Both independently compute the same shared secret.
9. The shared secret is converted into a 32-byte AES key for encrypted communication.

**Public Key Generation:**

- Alice: `A = g^a mod p`
- Bob: `B = g^b mod p`

**Shared Secret Calculation:**

- Alice: `s = B^a mod p`
- Bob: `s = A^b mod p`

Both calculations produce the same shared secret:

`s = g^(ab) mod p`

**AES Key Derivation:**

The shared secret is converted into a 2-byte representation and repeated 16 times to generate a 32-byte AES key.

Unlike Protocol II, the AES key is never directly transmitted between Alice and Bob.

**Files:**
- `new_alice_3.py`
- `new_bob_3.py`
- `common_3.py`

### Protocol IV: Invalid DH Parameter Detection

**Objective:** Detect invalid Diffie–Hellman parameters and return the appropriate error message.

**Procedure:**

1. Bob intentionally generates invalid DH parameters.
2. Bob sends the parameters to Alice.
3. Alice verifies whether `p` is a valid prime number.
4. Alice checks whether `g` is a valid generator.
5. If validation fails, Alice sends an error response with `opcode: 3`.
6. The communication terminates after the error is reported.

**Test Case 1: Invalid Prime Number**

Bob sends an invalid prime parameter, such as `p = 480`.

Expected response:

```json
{
  "opcode": 3,
  "error": "incorrect prime number"
}
```

**Test Case 2: Invalid Generator**

Bob sends a valid prime number `p = 499` with an invalid generator `g = 1`.

Expected response:

```json
{
  "opcode": 3,
  "error": "incorrect generator"
}
```

Alice uses primality testing and generator validation to identify the error type.

## 6. Key Concepts

| Concept | Description |
|---|---|
| RSA | Asymmetric cryptography using public and private keys |
| AES | Symmetric encryption using a shared secret key |
| Diffie–Hellman | Key agreement without directly transmitting the shared secret |
| Modular Exponentiation | Mathematical operation used in RSA and DH |
| Modular Inverse | Used to calculate the RSA private exponent |
| Prime Verification | Checks the validity of cryptographic parameters |
| Generator Verification | Verifies that a DH generator has the required order |
| Base64 Encoding | Converts encrypted binary data into text for JSON transmission |

## 7. Security Considerations

This project is intended for educational purposes.

The implementations use simplified cryptographic configurations to demonstrate how the protocols work.

- RSA and DH use small prime numbers for easier implementation and verification.
- Protocol II encrypts individual AES key bytes using textbook RSA without randomized padding.
- AES-ECB is used to demonstrate symmetric encryption, but it does not hide repeated plaintext patterns.
- Protocol III derives the AES key by repeating the shared secret rather than using a cryptographic key derivation function.
- DH parameters and exchanged public keys are not authenticated, leaving the protocol vulnerable to man-in-the-middle attacks.

Real-world secure communication should use established cryptographic libraries and protocols, sufficiently large keys, authenticated encryption such as AES-GCM, and secure key derivation methods.

Together, these protocols provide practical experience with asymmetric encryption, symmetric encryption, key exchange, cryptographic validation, and socket-based communication in Python.
